## 2. 回答：r31–r34（及同类产物）到底要不要重跑？

### 2.1 结论层面：**不需要重跑，采信文档值即合规**

理由是三条硬证据，不是"省事"：

1. **结论已固化且可追溯**：R3.1（4/39 + 6/35 翻转）、R3.2（3/26）、R3.3（1/41）、R3.4（0 翻转，S_eng−V0 HAC 3.32 等）已写入
   `docs/优化计划_V5_重规范_2026-09.md` §1 状态表与 §4 执行日志，逐条带产物路径与统计口径。
2. **三轮重建逐位一致**：M11 根因勘正文 §3 实测——R3.x 结论在三轮全链重建中**逐位一致**。
3. **对漂移免疫有机制解释**：M11 的根因是"并列分槽位裁决"，只影响端到端交易序列；
   **IC / 相关 / t 值不依赖行序**，故 R3.x 类统计天然免疫，B2.x 类端到端数字才受影响（±0.6pp 窗口）。

叠加铁律 3"任何实测结论以 **commit 后**的台账/计划文档为准" ⇒ **重跑不是结论有效性的前置条件。**

### 2.2 产物层面：重跑的唯一正当理由，且在沙箱内不成立

唯一正当理由是 **M9（产物哈希 manifest / 可复现）与审计可外验**：让未来的审查者能凭产物路径 + 指纹重建 byte-identical 的 CSV。
但 §1 已证明：**沙箱内 `output/` 在轮次之间必被清空**，在此重跑出来的 CSV 活不过一轮，
只能"跑完即抄数字进文档"，此时重跑的边际收益 ≈ 抄一遍已存在的数字，却要付出 40min 面板 + 各上游的 CPU。

### 2.3 因此：重跑分级（据此执行，不再一律重跑）

| 级别 | 项目 | 判断 | 理由 |
|---|---|---|---|
| **不重跑** | R3.1 / R3.2 / R3.3 / R3.4 的**结论** | 采信文档值 | §2.1 三条证据 |
| **不重跑（默认）** | R3.4 产物（`r34`，需 `factor_study.py` 变体面板） | 结论采信文档；产物标 `【历史产物·未重跑】` | 唯一"贵"的 R3 项（成本未实测，疑 1–4h），收益仅为补 CSV |
| **不重跑（默认）** | M1.2 余项（`m12b`，需 `p4_alpha_decay.py` + `rbsa_ew_study.py`） | 结论采信文档（HP4A-3 OOS t 1.61、S3r 2.06） | 同上，两个上游成本未实测 |
| **P0 必跑** | `build_navadj.py`（38s）+ **规范面板** + `b21_baseline.py` | 跑 | 地基层：b21 的 R0→R3 分解（+5.08/+8.59/+10.73/+10.84%，MaxDD −18.5%）是 B2.2/B2.3/S6.2/C1·C2 的共同输入与唯一权威基线；D0.2 同时对拍跨机一致性 |
| **P1 跑（便宜）** | `r31`（分钟级，直接吃面板） | 跑 | 成本近零，产物是 F7.2 勘误的引用对象，顺手补齐 |
| **P1 跑（便宜）** | `r32`（自带 `regen=True`，只需面板）、`r33`（只需 `p2_vol_build.py`，~1–3min） | 跑 | 见 §3 勘误：二者实为分钟级，原判断过重 |
| **P1 跑** | `b22_b23.py`、`c_experiments.py` | 跑 | 只需面板 + navadj；C1/C2 已裁决，重跑仅为产物补齐与数字复核 |
| **P2 探针后定** | `s62_param_grid.py`（243 格） | 先测单格成本 | 结论已入库（基线分位 82%）；若单格成本使总量 >2h，降级为"采信文档" |
| **用户本机** | S6.1（11 组面板）、R3.5（动物园） | 本机跑 | 小时级，且需要实物产物留存 |

### 2.4 处置规则（防止"重跑"变成"偷偷改结论"）

1. **先采信文档值**：任何重跑完成前，对外结论一律引用文档中的已固化数字。
2. **重跑值与文档值不一致时，禁止直接改文档**。处置顺序固定为：
   ① 排查环境（numpy/pandas 版本、行序/并行度）；② 排查口径（是否误用 SURV/FULL-PIT、标签对齐）；
   ③ 仍不一致 → 按 §0.3 **翻案规则**处理（HAC 口径下翻转 + 双窗同向才可改判，且以追加段记录、原文保留）。
3. **产物状态如实标注**：未重跑的产物在 manifest 与报告中标记 `【历史产物·未重跑·结论采信文档】`，
   **禁止**把"结论有效"包装成"产物在手"。

## 4. 针对"易失沙箱"的新执行范式

| 载体 | 能留下什么 | 该干什么 |
|---|---|---|
| 沙箱（易失） | **只有"小且可提交"的东西**：指纹数字、汇总表、manifest 行、文档 | 跑便宜的链 → **立刻把数字抄进 docs/ 并 commit + push**；不指望大 CSV 留存 |
| GitHub（持久） | 文档、代码、指纹 | 每个工作单元结束必须 `git push`；下一轮开场先校验本地 HEAD 是否被回滚 |
| 用户本机（持久） | 全部实物产物（面板、缓存、CSV） | 小时级任务 + 长期持有产物；只回传小汇总 |

**跨机一致性闸门（给本机跑的任务用）**：
- **一级闸门（推荐，38 秒）**：本机跑 `python build_navadj.py --workers 4` → 与本文档/`优化计划_V5 §1/D0.2` 的权威值对账：
  池 4,987 只、事件 21,454（12,090 / 9,248 / 116，覆盖 3,494 只）、年化差 均值 +0.6215%/yr / P95 +3.91% / max +78.78%（n=4,090）。
  **四项全同**才继续下游；不同即停机排查（净值缓存或 pandas 版本差异）。
- **二级闸门（可选）**：规范面板 159 个月逐月 `n_elig` 序列指纹（若沙箱本轮能跑完面板，将落成 tracked 文件 `docs/V5_规范面板逐月合格数指纹_*.csv`）。

## 5. 纪律更新（追加到铁律清单，不删原文）

- **铁律 3 修订（由本次事故证成）**：本地 commit 不防重置，"已 commit" ≠ "已落地"。
  **只有 push 到远端的引用、以及已 push 文档中固化的数字，才算落地。**
- **铁律 8（新增）**：每轮开场先执行
  `git fetch origin arena/01a05f52-quant-fund-picker && git log --oneline origin/arena/01a05f52-quant-fund-picker -3`，
  与本地 `git log -1` 比对；若本地 HEAD 落后/被回滚 → `git reset --hard origin/arena/01a05f52-quant-fund-picker` 恢复后**再**动手，
  避免在陈旧历史上重复劳动。
- **铁律 9（新增）**：沙箱内不发起"活不过一轮"的重活；估算 >1h 且产物不可压缩为小指纹的任务，一律转用户本机。
