## 2. 根因勘正：B2.x 轮间数字漂移 ≠ T+1 实现错误，而是 M11（并发构建行序非确定）

**观测矛盾**（这是逼出真相的实验串）：
1. 三轮全链各自重建产出不同 B2.1 数字：R1 trades = 76 / 81 / 76，R2 = 78 / 83 / 78，R3 = 78 / 94 / 78，
   R0 恒为 119 笔但 CAGR 在 +6.70/+6.74/+6.72% 间漂移；
2. 决定性对照：同环境下 `backtest_local.simulate` 自身轮间结果也不同（76↔81）——
   而 legacy 引擎从未被改动 ⇒ **差异只能在面板输入，不在执行实现**；
3. 同时 R3.1–R3.4（IC 类）三轮统计逐位一致——因为 IC/相关/t 值**不依赖行序**。

**根因（M11）**：面板/评分构建在 `ThreadPoolExecutor + as_completed` 下按**线程完成顺序**收集行；
`aggregate()`/`finalize()` 的 rank/S_total 值虽与行序无关（并列取均值），但**面板行序**影响下游
`groupby→set_index→sort_values("S")` 的**并列分平局次序** → `simulate` 买槽"谁先谁后"在 S 并列个案中不确定
（slots=10 满槽时，靠后者被丢弃）→ 交易序列逐轮漂移。成本/价格微差（round-3 换了 numpy 2.4.6）叠加 <0.03pp。

**性质评估**：
- 这不是交易/信号逻辑错误——**任何一只基金的得分没有任何一分变化**，变化的是并列个案的槽位裁决；
- 漂移窗口实测：R1 76↔81 笔、CAGR ±0.6pp；R2/R3 同量级；
- 一切 IC 类统计（R3.x 全部翻转判定）**经三轮验证对漂移免疫**。

**修复（commit 4a0e75e）**：
- `engine.finalize` 入参 rows 按 code 稳定排序（覆盖 harvest_date / factor_study / scan 全调用点）；
- `p1_panel_build.build_date` 评分结果先按 code 归位再聚合，S_total 展示排序改 mergesort 稳定序；
- `sim_core`＋`strategy_bt` 薄封装路径同受保护（并列分裁决自此确定性）；
- 环境钉版 `requirements-v5-lock.txt` 消除 numpy 末位漂移源。

**基线冻结规则（自本条生效）**：M11 修复后重建的面板为**唯一基准面板**；此前各轮 B2.x 数字
作为"漂移区间见证"披露在本文件 §3，不再作为任何裁决输入。
